# 阶段 1 复盘：从脚本原型到可安装的命令行工具

## 阶段目标与当前结论

本阶段围绕个人工具箱 `mytool` 的基础能力展开：让命令行入口能够接收管道输入，提供翻译与命令帮助问答，并能在不激活项目虚拟环境的情况下运行。

目前，`mytool` 已能通过 pipx 安装并从项目目录外启动，CLI 已接入 `trans`、`find`、`sum` 和 `ask` 四个子命令。语法、参数解析、空输入拦截、配置读取及四个命令的模拟调用经过本地检查。**这段开发记录中仍没有一次成功返回模型结果的真实 API 调用，因此模型效果和完整端到端流程尚未验证。** 此外，当前 pipx 安装的代码副本落后于仓库源码，重新安装前不能把源码检查结果当作全局命令的验证结果。

## 起点与实现过程

最初仓库只有一个尚未接通的 Python 工具箱草稿。`pyproject.toml` 声明了 `mytool.cli:main` 入口，但当时 `cli.py` 有错误的导入语句，也没有 `main()`；`trans.py` 在模块加载时直接读取标准输入并打印结果。`ask.py`、`find.py`、`summary.py` 与 `__main__.py` 当时为空，项目说明文件也没有内容。

1. **建立协作约定。** 新增根目录 `AGENTS.md`：默认用中文、按 Python 初学者的程度分步指导；讨论本身不授权修改文件，明确的修改请求则视为授权；运行可能收费的外部 API 前先征得同意。该文件的“项目现状”部分随后没有同步更新，现已过时。
2. **接通翻译入口。** 将翻译逻辑整理为接收文本并返回译文的 `translate(text)`；`cli.py` 负责解析 `trans` 子命令、读取标准输入和打印结果。补上 `main()` 和正确的 Python 导入路径。随后把 `sys.stdin.read()` 移到参数解析之后，避免 `--help` 先等待输入；用 `text.strip()` 拦截空字符串及只有空白字符的输入。
3. **修复安装配置。** 第一次执行 `pip install -e .` 时，setuptools 在根目录同时发现 `mytool` 和 `reference`，拒绝自动打包。`pyproject.toml` 随后明确只查找 `mytool*`。添加 `openai` 与 `python-dotenv` 依赖时，还纠正过 TOML 字符串引号、`dependencies` 拼写及其必须位于 `[project]` 下的问题。
4. **确定 `find` 的交互形式。** 最初想运行 `docker --help | mytool find` 后再交互输入问题；但管道占用了标准输入，普通 `input()` 会误读帮助文本。最终约定让帮助文本走标准输入，问题作为位置参数，例如 `docker --help | mytool find "怎么删除镜像？"`。`find(text, question)` 已接入 CLI，`trans` 和 `find` 因参数个数不同而分别分发。
5. **改进 `find` 的回答约束。** 原提示词没有清楚划定依据，容易让模型补猜命令。现在的规则是：只依据给定帮助文本；能确定完整用法时给出命令和简短解释；只发现相关子命令时建议查看它的 `--help`；没有相关内容时明确说无法判断。帮助文本与问题被放在同一条带标签的用户消息中。还为消息列表增加了 SDK 消息类型标注，解决编辑器可能出现的类型提示问题。
6. **让命令脱离项目虚拟环境。** 讨论了 shebang、执行权限、`.zshrc`、符号链接和 pipx：shebang 不会自动赋予执行权限，直接运行模块也不会自动进入 CLI；把项目 `.venv/bin` 写入 `.zshrc` 仍依赖项目路径。最终使用 pipx 安装 `mytool`，由 pipx 管理独立环境并提供全局命令。
7. **处理配置与代理。** 从项目外运行时，默认 `load_dotenv()` 找不到原先依赖工作目录的 `.env`。目前由 `mytool/config.py` 统一读取 `~/.config/mytool/.env`，并为命令创建客户端。pipx 环境首次执行翻译时又因系统设置了 SOCKS 代理、环境中缺少 `socksio` 而在创建网络客户端时失败；项目依赖现已加入 `httpx2[socks]`，当时的 pipx 环境也检测到 `socksio`。
8. **收紧凭据与忽略规则。** 项目根目录的多余 `.env` 已移除，保留的 `~/.config/mytool/.env` 权限已收紧为 `600`。新增 `.gitignore`，忽略 `.env`、虚拟环境、Python 缓存、构建目录和 egg-info 元数据。这解决了先前文档记录的明文配置副本及生成物缺少忽略规则的问题。
9. **接入另外两个命令。** `ask.py` 和 `summary.py` 已从草稿接入 CLI，命令名分别是 `ask` 和 `sum`。`ask` 与 `find` 一样接收管道文本和问题参数；`sum` 与 `trans` 一样只接收管道文本。四个命令的 CLI 路由和模拟客户端调用均通过本地检查。
10. **集中处理常见错误。** `create_client()` 在缺少 API key 或 base URL 时抛出明确错误；CLI 将该错误及 SDK 的 `APIError` 转成简短提示，并在模型返回 `None` 时提示没有返回文本。相关路径用模拟结果检查过，尚未覆盖所有网络异常。
11. **重新确定验收重点。** 最近的讨论发现，继续整理小细节已偏离核心目标。对阶段 1 更有价值的下一步是让全局安装的命令与当前源码一致，再确认 `trans` 和 `find` 的真实使用流程。对比源码与 pipx 安装副本时，`cli.py`、`trans.py`、`find.py` 的文件哈希不同，说明目前全局命令尚未包含所有最新修改。

讨论中还明确了几个 Python 包概念：`__init__.py` 可以留空；`__main__.py` 用于支持 `python -m mytool`，但当前仍为空；`mytool.egg-info/` 是安装生成的元数据，不是业务源码。

## 当前接口与验证结果

- **安装入口：** `pyproject.toml` 指向 `mytool.cli:main`。从 `/tmp` 运行 `mytool --help`，可显示 `trans`、`find`、`sum` 和 `ask`；但 pipx 安装副本仍需与源码同步。
- **`trans`：** 从标准输入读取待翻译文本，调用 DeepSeek 兼容接口并打印返回内容。本次记录中没有确认真实 API 成功返回。
- **`find`：** 从标准输入读取帮助文本，问题取自命令参数。`mytool find --help` 正常显示必填的 `question`；消息构造和 CLI 路由曾用模拟返回值做过本地检查，尚未验证真实模型回答。
- **`sum`：** 从标准输入读取文本并生成摘要；CLI 路由和模拟客户端调用已经检查，真实输出尚未验证。
- **`ask`：** 从标准输入读取参考文本，并从命令参数读取问题；CLI 路由和模拟客户端调用已经检查，真实输出尚未验证。
- **输入检查：** 空输入和只有空格、换行的输入会显示参数错误并以退出码 2 结束，不进入 API 调用。
- **配置和错误：** `mytool/config.py` 统一读取用户配置文件并创建客户端。缺少配置、SDK 抛出 `APIError` 及模型返回 `None` 的路径已用模拟方式检查。检查没有显示配置值。
- **本地检查：** Python 源文件通过语法解析，`pyproject.toml` 可解析；四个命令的分发和模拟请求均通过检查。这些结果不等于网络请求或回答质量测试。

## 当前问题与改进点

### 已解决的阶段 1 问题

- 根目录多余 `.env` 已移除，保留的用户配置文件权限已收紧为 `600`；`.gitignore` 已覆盖凭据文件、虚拟环境和常见构建产物。
- 配置读取与客户端创建已集中到 `mytool/config.py`；CLI 已为缺少配置、`APIError` 和模型返回 `None` 提供简短提示。
- `ask`、`sum` 已接入 CLI；四个命令的参数分发和模拟客户端调用已通过本地检查。

### 仍需完成的核心验证

- 源码与当前 pipx 安装副本不同步。修改源码或依赖后需执行 `pipx reinstall mytool`，再从项目外确认全局 `mytool` 使用的是新版本。
- 在明确同意调用可能收费的 API 后，分别用真实请求验证 `trans` 与 `find`：检查退出状态、实际输出，以及 `find` 是否遵守“只依据帮助文本”的约定。`ask` 与 `sum` 同样尚未验证真实模型输出。
- 目前已处理 SDK 的 `APIError`，其他可能出现的网络或代理异常仍需结合实际故障检查。`find` 的回答约束目前也只有提示词和模拟测试支持。

### 后续改进点

- 四个命令仍分别编写请求逻辑，存在重复代码；稳定实际行为后可抽取共用部分。命令模块末尾无效的 `assert("hello,world")`、部分未使用的导入也可清理。
- `find` 和 `ask` 尚未校验空问题，过长的输入也没有明确处理策略。这些边界可在真实使用暴露需求后安排。
- 仓库尚无正式自动化测试；此前的模拟检查是临时验证。需要建立可重复运行的本地测试，覆盖 CLI 分发、配置缺失和模拟响应。
- `README.md` 已更正文件名，但内容仍为空；`AGENTS.md` 的“项目现状”仍描述早期语法错误和空模块，需要按现状更新。
- `__main__.py` 仍为空，因此 `python -m mytool` 不会进入 CLI。只有需要这种启动方式时才需补上。

## 阶段 1 的共识

- `mytool` 是管道友好的命令行工具：文档或待处理文本走标准输入，附加问题走命令参数。
- CLI 负责解析参数、输入校验、分发和输出；具体命令函数负责处理文本并返回结果。
- `find` 默认只依据传入的帮助文本回答，不确定完整用法时先建议查看更具体的 `--help`，不补猜参数。
- 配置与项目工作目录分离；日常使用由 pipx 提供命令，不依赖激活项目虚拟环境或在 `.zshrc` 中写入项目路径。
- 本地语法和模拟检查、真实 API 验证必须分开报告；尚未执行的网络验证不能记为通过。
- 阶段 1 下一步优先完成已安装命令与当前源码的一致性检查和真实使用验证，再决定哪些细节值得继续完善。
