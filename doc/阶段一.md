# 阶段一：mytool 基础能力、翻译缓存与 man 阅读方向

本文合并原有的《阶段 1》《阶段 2》和 `trans` 缓存对话总结。前期记录中的“当前状态”以编写当时为准；下文按现在的仓库代码区分已经实现的功能、验证结果和仍处于讨论阶段的设想。

## 目标如何变化

项目起点是一个从终端管道读取文本的 Python 个人工具箱。最初围绕 `trans` 翻译、`find` 命令帮助问答，以及如何安装和调用命令展开。后来接入 `sum` 和 `ask`，但讨论逐渐明确：项目应解决终端技术文本的实际阅读问题，不必为了凑齐工具箱功能继续增加命令。

最确定的日常场景是读懂 `docker --help` 等英文帮助。进一步的需求是发现、阅读和复用较长的 `man` 手册译文；日志问答与摘要也是探索过的方向。阶段一完成了可运行的 CLI 骨架和 `trans` 本地缓存，并讨论了 `man` 阅读库的设计，尚未实现 `man` 子命令。

## 从原型到命令行工具

1. **建立协作约定。** 根目录 `AGENTS.md` 约定用中文按 Python 初学者的程度分步说明；讨论本身不授权修改文件；调用可能收费的 API 前需征得同意。其早期“项目现状”曾过时，后来已更新。
2. **接通 CLI。** 起初 `pyproject.toml` 虽指向 `mytool.cli:main`，`cli.py` 却有导入错误且未定义 `main()`，`trans.py` 也曾在模块加载时读取标准输入。现在由 CLI 先解析参数、再读取并校验标准输入、分发子命令并输出结果；`mytool/__main__.py` 已支持 `python -m mytool`。
3. **接入四个命令。** `trans` 翻译成中文；`find` 依据传入的命令帮助回答问题；`sum` 总结文本；`ask` 根据传入文本回答问题，当前提示词侧重日志分析。`find` 和 `ask` 的问题通过位置参数传入，因为管道已占用标准输入，不能再可靠地用 `input()` 读取问题。`trans` 和 `sum` 只需管道文本。
4. **约束 `find` 的回答。** 帮助文本和问题被放在带标签的用户消息中。提示词要求只依据提供的帮助文本：能确定完整用法时给出命令和简短解释；只看到相关子命令时建议查看它的 `--help`；信息不足时明确说明无法判断。曾为消息列表补充 SDK 类型标注。提示词约束尚未经过真实模型回答验证。
5. **修复安装。** 第一次 `pip install -e .` 因根目录同时存在 `mytool` 与 `reference`，触发 setuptools 的多顶层包发现错误；随后在 `pyproject.toml` 中限定只查找 `mytool*`。添加依赖时也修正过 TOML 引号、`dependencies` 拼写和字段所在位置。
6. **让命令离开项目虚拟环境。** 讨论了 shebang、执行权限、`.zshrc`、符号链接和 pipx。shebang 本身不会赋予可执行权限；把项目 `.venv/bin` 写入 shell 配置仍依赖项目路径。最终采用 pipx 提供全局 `mytool` 命令。普通 `pipx install .` 使用安装时的代码副本，修改源码后需确认安装版本是否同步。
7. **配置和运行错误。** `mytool/config.py` 从 `~/.config/mytool/.env` 或同名环境变量读取 `DEEPSEEK_API_KEY`、`BASE_URL`，创建 API 客户端，避免依赖当前工作目录。曾因 SOCKS 代理环境缺少 `socksio` 无法创建客户端，项目依赖随后加入 `httpx2[socks]`。CLI 对缺少配置、SDK 的 `APIError` 和返回 `None` 提供简短提示。
8. **整理项目文件。** 项目根目录多余的 `.env` 已移除，保留的用户配置文件权限曾收紧至 `600`；`.gitignore` 覆盖凭据、虚拟环境、缓存和构建产物。`README.md` 已补项目介绍、安装配置、使用示例、目录结构、贡献方式和许可证现状。`__init__.py` 可保持简短；`mytool.egg-info/` 是安装元数据，不是业务源码。

## trans 缓存：需求、取舍与现状

`docker --help` 一类文本通常会反复阅读。每次翻译相同内容都请求模型，会增加等待时间和调用成本，因此决定先用 Python 标准库 `sqlite3` 建一张表，把成功返回的译文留在本机。最初想将写入和匹配拆为 `insert.py` 与 `Match.py`；后来统一放在 `mytool/cache.py`，让建表、查询、保存共用数据库结构。缓存模块只存取数据；CLI 负责打印。

### 从“按来源”到“按原文”

早期方案把 `docker --help` 作为来源标识，连同命令输出和译文存入表中。同一来源输出变化时可覆盖旧译文。实现过程中曾加入 `--source "docker --help"` 和 `--refresh`，但每次使用管道都要重复输入来源，违背了便捷使用的目标。

普通管道右侧只能可靠收到左侧命令的输出，无法从标准输入推知左侧写的是哪条命令。讨论过让工具自己运行命令的形式 `mytool trans -- docker --help`，其中 `--` 用于隔开工具参数和待执行命令；**这种命令执行模式没有实现**，管道模式仍是当前入口。

最终决定第一版只按完整原文精确匹配，取消 `--source`：

```sh
docker --help | mytool trans
docker --help | mytool trans --refresh
```

当前 `mytool/cache.py` 使用 `~/.local/share/mytool/trans.db`。唯一的 `translations` 表包含 `original_text`、`translated_text`、`updated_at`，以完整原文为主键。`init_db()` 建表，`lookup(text)` 查找，`save(text, translation)` 插入或更新。`translate(text, refresh=False)` 在命中时直接返回旧译文；未命中或指定 `--refresh` 时才创建客户端并请求模型。调用抛出异常或返回 `None` 时不写入。`--refresh` 跳过查询，返回译文后更新相同原文的记录。

原文匹配包括空格和换行。输出变化会产生新记录，不会自动覆盖旧原文的记录。缓存不识别帮助文本对应的命令，模型或提示词更改也不会自动使旧译文失效。数据库放在用户数据目录，是为了避免把运行时数据放进项目源码或可能在 pipx 重装时被替换的安装包副本；API 配置仍放在 `~/.config/mytool/.env`。

### 实现时遇到的问题与速度排查

用户初写的 `cache.py` 已划分建表、查询、保存，但初始化与保存连接了不同数据库文件；表缺少查询需要的 `source` 列和唯一约束；查询 SQL 拼接缺空格；模块导入时创建的全局连接关闭后又被复用。后来统一路径，改为各操作自行打开和关闭连接，再按最终需求将表改成原文主键。

用户曾反馈“数据库已有记录但读取仍很慢”。排查当时的运行环境时，程序指定的 `~/.local/share/mytool/trans.db` 并不存在，因此无法证明那次调用命中了缓存；也没有拿到用户当时执行的完整命令。一次本地计时中，100 次模拟缓存查询约 35 毫秒，`mytool trans --help` 启动约 0.76 秒，`docker --help` 约 0.05 秒。这些只是当时环境的观察，不代表真实端到端耗时。改为按原文匹配后，也消除了漏写 `--source` 导致不读写缓存的路径。

## man 阅读库：已讨论、未实现

更长远的需求是：从某篇手册发现还可以读哪些相关手册，选择后阅读整篇中文译文，并逐渐积累可搬运、可复用的个人译文库。只翻译用户已经知道名称的手册，不能解决“我不知道还有 `docker-run`”的问题。第一版决定以**整篇手册**为翻译和缓存单位，不拆到章节或选项；译文按需加入，不预先翻译整套手册。相关手册可以平级保存，不需要手工维护严格的父子树。

用户检查过本机 Docker 手册，得到以下观察：

1. `man -w docker` 返回 `/usr/share/man/man1/docker.1.gz`。压缩文件含 `.TH`、`.SH NAME`、`.SH SYNOPSIS` 等 roff 标记；`man` 阅读器中的翻页不等于文档章节。
2. `docker.1.gz` 有 `NAME`、`SYNOPSIS`、`DESCRIPTION`、`OPTIONS`、`COMMANDS`、`EXAMPLES`、`HISTORY` 七个 `.SH` 标题。其 `COMMANDS` 章节只提示查看 `docker help` 或 `docker --help`，**没有列出 `docker-run`**。因此不能声称只读 `man docker` 就能发现它。
3. 本机另有独立的 `docker-run.1.gz`；其中一个选项可能由多个 `.PP` 段落说明，不能简单把 `.PP` 当作选项边界。这个观察帮助理解源格式，但当前方案不拆分翻译单位。
4. `man -k docker` 会匹配名称及简短描述，直接展示全部结果可能过于嘈杂。曾讨论“精确名称优先、再看 `docker-` 前缀、允许进一步筛选”，但未定为最终规则；候选也不能自动视为真实子命令或完整列表。

讨论中的入口为 `mytool man <名称>`。它可能查找本机手册，提供中文阅读指南和相关手册候选，并按需翻译或复用整篇译文。找不到手册与找到但未翻译，需要不同提示。系统 `man` 可以产生排版后的可读文本，避免直接把 roff 标记交给模型；`man -w` 的源文件位置可以辅助识别版本或变化。发现相关手册还需结合本机手册索引等可验证来源，不能仅依赖当前手册内容。

以上均为设计方向：`mytool/commands/man.py` 目前为空，CLI 未注册 `man`；首次打开时是否立即翻译、如何筛选和选择候选、交互与非交互模式、重新翻译、版本识别、缓存导入导出都尚未确定。不能把这些设想写成已有功能。

## 验证边界与后续问题

- 已做过 Python 语法解析、TOML 解析、CLI 帮助和命令分发检查，以及使用临时 SQLite 数据库和模拟翻译器验证缓存命中、原文变化、`--refresh`、模型返回 `None` 时不写入。其他三个命令也做过模拟分发。这些检查没有调用真实 API。
- 当前记录中没有一次可确认的真实模型成功返回，因此翻译质量、`find` 的依据约束，以及真实缓存命中后的端到端耗时都不能记为已验证。README 的安装说明和全局命令的当前版本也需按实际安装环境检查。
- 仓库没有正式自动化测试配置；四个命令仍有重复的模型请求逻辑。`find`、`ask` 的空问题、长输入边界，缓存旧记录清理与提示词版本失效，都可在实际使用中继续评估。
- 下一步若推进 `man`，应先确认完整阅读流程、候选来源与版本识别，再实现命令；不要把探索时假设的示例输出当作已承诺的行为。
